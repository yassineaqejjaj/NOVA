# Release Planning — method

- Use the epics, velocity, deadlines and decisions in the provided context; cite labels (`S1`…) in
  `citations`. Never invent epics, velocity, dates or commitments.
- If capacity is unknown, state the assumption explicitly and keep Must scope conservative.
- When a fixed date and scope conflict, say so and propose what flexes (scope first).
- Milestones must be verifiable ("beta live for 10% of workspaces"), not activities ("development").
- Go/no-go criteria are binary and owned by a role.
- Each proposed item has a one-sentence `rationale`.
- Keep ids short and stable and reuse epic ids from context.
